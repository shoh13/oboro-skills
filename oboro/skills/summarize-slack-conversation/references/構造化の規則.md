# 構造化の規則

手順 3 で作った正規化済みテキストとソースポインタを、原文へ追跡可能な構造化結果へ変換する規則。2026-11-28 まで別のスキル `discussion-synthesis` だったものを、呼ぶのがこのスキルだけになったので移した。

## 入力


- 正規化済みテキスト：手順 3 で原文を読み取り、ソース固有の構造を失わない形で整えた本文
- ソースポインタ：`pointer_id`、発言・段落・時刻・見出し・ブロックなどのsource descriptor、参照先の原文文字列を持つ、結果を原文へ対応付けられる識別子
- 出力対象：必要な出力項目と、ページで使う表記・粒度

入力がURLだけ、取得指示だけ、または未読のソースだけなら構造化せず、不足として止まる。

## 共通変換

1. 入力を、事実、提案、決定、未決、依頼・行動、用語、前提・文脈へ分類する。
2. Evidence-backed facts、Decisions、Open questions、Actions、Termsの各項目に、1つ以上の解決可能なソースポインタを保持する。
3. 明示された内容と推測を分離する。入力から合理的に推測できても明示されていない内容は、Evidence-backed facts、Decisions、Open questions、Actionsへ入れない。必要な場合だけAssumptions/Contextへ「推論・非確定」と明記して置き、行動や未決へ昇格させない。
4. Open questionsへ入れられるのは、入力に質問、未決、未確定、要確認、不明、保留として明示された項目だけとする。「次に確認するとよい」「通常必要」など、推論した不足を追加しない。
5. Actionsへ入れられるのは、入力に担当、約束、依頼、命令、期限付き行動として明示された項目だけとする。best practiceや自然な次工程を生成しない。
6. 重複を統合し、矛盾や記録差を隠さず残す。
7. Code token、version、identifier、proper noun、数値、単位、引用句をsource span fidelity対象として扱う。出力へ含める場合は、対応するソースポインタ先の文字列を完全一致でコピーし、正規化・省略・言い換えをしない。例：`v2 endpoint`、`OAuth PKCE`、`S1`、`90日`。
8. 各出力itemへ一意な`item_id`と`source_pointer[]`を付ける。`source_pointer[]`の各要素には`pointer_id`、source descriptor、解決結果、当該itemでsource entailmentを検査する対象を明示し、itemとpointerの1対多対応を保持する。
9. item単位のpreflightとして、pointer解決、source entailment、source span fidelity、token preservationを検査する。pointerが未指定・解決不能、またはpointer先がitemを直接支持せずsource entailment不成立なら、1件でも入力全体をatomic fail-closedとし、`status=input_required`で停止する。
10. atomic fail-closed時は`diagnostics`だけを非空で返し、Summary、Evidence-backed facts、Decisions、Open questions、Actions、Terms、Assumptions/Context、Source pointersの8成果カテゴリと全本文候補を空にする。解決済みitem、入力中に明示された未決・Actionも部分返却しない。`write_gate=false`とし、ページへの書き込みを0件にする。
11. atomic fail-closed時の`diagnostics`には、実際に失敗した`item_id`、`pointer_id`、source descriptor、reason、restart requirementだけを記録する。restart requirementは、失敗pointerを同じitemへ解決可能かつentailment成立の状態で再提示し、当該itemのpreflightから再開することを示す。
12. pointerはitem間で代用しない。pointer `P1`が別itemの根拠である場合は流用せず、1件のpointer解決失敗またはentailment不成立を別pointerへ付け替えない。
13. 返却直前に全返却候補を対象としたtoken preservation検査を行う。意味を変えるtokenの脱落・追加が見つかったitemは返却せずdiagnosticsへ回し、必須itemなら同じatomic fail-closedを適用する。
14. 出力対象だけを作り、ページの形式への変換は SKILL.md の手順 5 で行う。

## 出力Contract

- Summary：目的、主要論点、結論を簡潔にまとめた要約
- Evidence-backed facts：入力に明示された確認済み事実。各項目に1つ以上の解決可能なソースポインタを付ける
- Decisions：入力で明示的に確定した決定。各項目に1つ以上の解決可能なソースポインタを付ける
- Open questions：入力で質問、未決、未確定、要確認、不明、保留と明示された項目だけ。各項目に1つ以上の解決可能なソースポインタを付ける
- Actions：入力で担当、約束、依頼、命令、期限付き行動として明示された項目だけ。各項目に1つ以上の解決可能なソースポインタを付け、担当・期限は入力にある場合のみ記載する
- Terms：入力に現れる用語、略語、固有名詞と入力文脈での意味。各項目に1つ以上の解決可能なソースポインタを付ける
- Assumptions/Context：明示された前提・制約・背景。入力からの推論を置く場合は「推論・非確定」と表示する
- Source pointers：各出力itemの`item_id`から、`pointer_id`、source descriptor、解決結果、entailment対象へ戻れる対応表
- 状態：`status=complete`、`status=input_required`、`status=conflict`のいずれか

該当情報がない項目は空配列または「該当なし」として返す。特にOpen questionsとActionsは、根拠がなければ空のままとし、埋めるために生成しない。

各出力itemは`item_id`と`source_pointer[]`を持つ。SummaryとAssumptions/Contextを含め、ソースに基づく記述は対応するpointerを明示する。

`diagnostics`には、dropped itemの`item_id`、exact reason、failed `pointer_id`、source descriptor、restart requirementを記録する。pointer不足時は、実際に失敗したitemとpointerだけを報告し、別item・別pointerへ付け替えない。`diagnostics`は8つの成果物項目には含めず、成果物本文へ混ぜない。

## 完了条件

- 指定された8つの出力項目と状態が返されている。
- 事実、決定、未決、行動、推測が混同されていない。
- Evidence-backed facts、Decisions、Open questions、Actions、Termsの全項目が`item_id`と1つ以上の解決可能な`source_pointer[]`を持ち、pointerごとの解決結果とentailment対象が明示され、参照先が主張を直接支持している。
- source span fidelity対象の文字列がソースポインタ先と完全一致し、token preservation検査で意味を変えるtokenの脱落・追加が0件である。
- pointer-item対応の誤付替えと、別itemのpointerによる代用が0件である。
- 入力に明示されていない内容をEvidence-backed facts、Decisions、Open questions、Actionsへ補完していない。
- 担当、期限、役割、略語展開を入力外から補完していない。
- 根拠のないOpen questionsとActionsを生成せず、空配列または「該当なし」を許容している。

## 不足時

- 不足項目、処理できない理由、必要な入力、停止地点を返す。
- 必須のソースポインタが未指定または解決不能なら、`status=input_required`、返却候補0、書き込み不可として停止し、解決可能なポインタが渡されるまで項目を確定しない。
- `diagnostics`に、dropped itemの`item_id`、exact reason、実際に失敗した`pointer_id`とsource descriptor、restart requirementを記録する。失敗を別pointerへ付け替えない。

## 禁止事項

- 構造化の段階で、Notion、Slack、ファイル、外部サービスから新たにソースを取得する。
- 会話に代わって意思決定する、承認する、優先順位を確定する。
- 入力にない決定、担当、期限、役割、意図、URLを作る。

## 検証

- 構造化は正規化済みテキストだけで行い、新たなソース取得を試みていない。
- 8つの出力項目と状態がContractどおりである。
- Evidence-backed facts、Decisions、Open questions、Actions、Termsの全件に`item_id`と1つ以上の解決可能な`source_pointer[]`がある。
- 各pointerの解決結果とentailment対象が対応するitemへ明示的に結び付き、ポインタ先が主張を直接支持している。
- source span fidelity対象が参照先の文字列と完全一致し、token preservation検査で意味を変えるtokenの脱落・追加が0件である。
- pointer-item対応の誤付替え、別itemのpointerによる代用、解決失敗の別pointerへの付け替えが0件である。
- `status=input_required`では返却候補0、書き込み0であり、diagnosticsが正しいfailed item/pointer/source descriptor/restart requirementを指す。
- Open questionsとActionsが空でもContractどおりと判定する。
- 入力に明示されていないActionまたはOpen questionが0件である。
- 推測と未確認事項が事実から分離されている。

### 静的例

| ケース | 入力上の要点 | 期待結果 |
| --- | --- | --- |
| 正常Slack | 決定、明示された未決、担当付きAction、解決可能な発言ポインタがある | 明示項目だけを分類し、各項目を発言へ追跡できる。自然な次工程や追加質問は生成しない |
| 正常technical | 技術的事実、決定、明示された要確認事項、依頼、用語、段落ポインタがある | 5分類の全項目が直接支持され、推論は必要な場合だけAssumptions/Contextへ「推論・非確定」として分離される |
| 空入力 | 正規化済みテキストが空、または必須ポインタが解決不能 | 状態を不足として入力待ちで停止し、8項目を補完生成せず、副作用0を維持する |
| 明示なしAction | 状況説明と決定はあるが、担当、約束、依頼、命令、期限付き行動がない | Actionsは空配列または「該当なし」。best practiceや自然な次工程からActionを生成しない |
| v2保持 | `v2 endpoint`を採用したという決定と、その文字列を含む解決可能なpointerがある | 出力でも`v2 endpoint`を完全一致で保持し、`v2`の脱落・正規化・言い換えをしない |
| 数値保持 | `90日`を含む事実または決定と、その文字列を含む解決可能なpointerがある | 出力でも`90日`を完全一致で保持し、数値・単位の脱落、追加、変換をしない |
| pointer misalignment拒否 | item Aの`P1`は解決可能、item Bの`P2`は解決不能で、各pointerのsource descriptorが異なる | `P1`をitem Bへ代用せず、`status=input_required`、返却候補0、書き込み0とし、diagnosticsはitem B／`P2`／そのsource descriptor／restart requirementを返す |
| Actionなし空配列 | 事実と決定はあるが、担当、約束、依頼、命令、期限付き行動がない | Actionsを空配列で返し、生成Action 0件を維持する |
