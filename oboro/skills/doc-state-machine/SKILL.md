description: "文書（指示書、要件定義書、仕様書、設計書、運用手順書など）の「この場合はこうする」という規定を、原文の節への対応と指摘（食い違い・記載のない点）つきの状態機械（ステートマシン）として単一の HTML に可視化・更新する。版の履歴の再生や判定表にも使う。コードの状態遷移図には使わない。"
---

文書の規定は節ごとに分散しており、読み手は、条件と結果の対応と処理の順序を頭の中で再構成している。このスキルは、規定を「状態 → 条件 → 遷移先」の枝として記載し、枝と原文の節を相互に移動できるページを作成する。

成果物は、同梱のテンプレート（`assets/template.html`）へデータを埋め込んだ単一の HTML である。作業の対象はデータだけで、ページの HTML・CSS・JavaScript は作成しない。`<skill-dir>` は、この `SKILL.md` を含むディレクトリである。

```text
<data-dir>/
├── meta.json      題名、原文、遷移先の種別、遷移の描画方法、用途、区分
├── machine.json   状態、枝、エラー、判定表
├── sections.json  原文の節の一覧
├── issues.json    指摘
├── timeline.json  版の年表（版の履歴を取得できる場合だけ）
└── hist.json      版ごとの変更の一覧（同上）
```

各項目の定義、build の検査の一覧、版の履歴の規則は `references/data-format.md`（契約）に記載している。データを作成する前に全文を通読する。この文書は項目の定義を再掲しない。

| 完成例 | 性質と使用している機能 | 手本とする点 |
| --- | --- | --- |
| `examples/poteto-mode/` | 版の履歴あり（Git、171コミット）。`flow`、`--items --arrows` で56節へ分割した原文、`rules` に配置した `stop` | 指示書の状態の構成、`h` の対応付け、`note` の指摘 |
| `examples/fixture/` | 全項目を1件以上使用 | エンジンの検査用。データの作成方法の手本にしない |

## 完了条件

全ての場合:

- `node <skill-dir>/scripts/build.mjs <data-dir> <out.html>` が `ok:` を出力し、HTML を出力した。
- build の出力の `sections:` が「参照なし 0」で、`src を持たない枝: 0` である。
- `issues.json` に、状態の名前と `flow` の順序が作成者の構成であることを記載した `note` がある（手順3）。
- ブラウザまたは jsdom で、読み込み時の例外が0件である。どちらも使用できない場合は、その旨を報告に記載した。
- 手順9の報告事項を全て記載した。公開先の指定がない場合は公開していない。

使用した機能に応じて追加する条件:

| 機能 | 条件 |
| --- | --- |
| `transitions: "explicit"` | build の出力の `到達 (<用途>): N / N` が全ての用途で一致する。一致しない場合は、`note: 到達できない状態` の各状態に、補完した遷移（`inferred` 付き）か `gap` の指摘がある |
| `table` | build の出力に `note: 未規定 (issue なし)` の行がない |
| `timeline.json` | build の出力の「枝に対応しないコミット」（`hist.json` に記載した版だけが対象）の全件が、意味の変化がない更新（文言の整理、原文の移動など）であることを確認した。`h` が空の枝を `note` の指摘に記載した |

## 文書の性質と使用する機能

機能は、文書の種類（指示書か要件定義書か）ではなく、次の表の性質で選択する。表の各行について該当するかを判定し、該当する行の機能を全て使用する。1つの文書が複数の行に該当する。判定と根拠は手順9で報告する。

| 文書の性質 | 使用する機能 | 判定の方法 |
| --- | --- | --- |
| 版の履歴を取得できる | `timeline.json`・`hist.json`・枝の `h`・注目（`star`）。手順6 | 版の一覧と、版ごとの本文を取得できる（Git 管理のファイルなど） |
| 版の履歴を取得できない | 年表を作成しない。現在の原文や推測から版を合成しない | 版ごとの本文を取得できない（Google Docs で `list_file_revisions` が空の結果を返却する、Git 管理でないファイルであるなど） |
| 処理の経路が分岐・省略・循環する | `transitions: "explicit"` と遷移先 `["state", …]`。到達性を確認する。手順3 | 用途や条件によって通過する状態が異なる、局面を省略する経路がある、前の局面を反復する記載がある |
| 経路が一直線か、局面の順序だけがある | `transitions: "flow"`（既定）。手順3 | 上の行に該当しない。「実装前」「コミット前」のような前後関係だけの記載を含む |
| 要求の拒否（エラーとする・受け付けない）を規定している | `errors`。手順5 | システムが入力・要求を拒否する規定がある。エージェントの「停止する」「確認を待つ」は拒否ではなく、`rules` に `stop` で配置する |
| 適用の対象が複数ある（用途・環境・役割など） | `meta.variants` と `for`。ある対象の規定をほかの対象へ展開しない。手順5 | 原文が対象ごとにタブ・節を分割している、または規定ごとに対象を明記している |
| 条件が2軸以上の組み合わせで決定される | `table`。記載のない組み合わせは未規定の欄とし、`gap` の指摘と関連付ける。手順5 | 2つ以上の条件の値の組ごとに、結果を規定している |
| 規格・原則を参照している | 適用する動作なら遷移先（`prin` など）、理由なら `why`。手順5 | 手順5の「規格・原則」の判定に準拠する |
| 要求の強さを区別して記載している | `level`。手順5 | 「望ましい」「してもよい」「当面実装しない」「試験的」などの記載がある |
| 標準からの逸脱・厳格化を記載している | `std`。手順5 | 標準（RFC など）と同じ・より厳格・逸脱であることを、原文が記載しているか、標準の本文と照合できる |
| 全ての文書 | `sections.json`・`src`・`issues.json`・`inferred` | — |

## 手順

### 1. 対象と文書の性質を確定する

次の項目を、依頼と利用者の設定（`CLAUDE.md` など）から確定する。判断できない項目だけを質問する。

- 原文: Google Docs の URL、Markdown のパス、GitHub のリポジトリとファイルのパスなど。Git 管理の場合は1ファイルを対象にする。
- 対象の範囲: Google Docs の URL の `tab=` は、依頼者が閲覧中のタブの指定にすぎない。依頼が「この要件」「この仕様」のように文書全体を指す場合は、全タブ（子タブを含む）を対象にする。依頼がタブや節の名前を明示している場合だけ、範囲を限定する。
- 年表の範囲とするパス（Git 管理の場合）: 原文と同じ単位（プラグイン、スキル集など）に属するファイルだけを含むディレクトリ。次のいずれかに該当する場合は、原文の1ファイルを範囲とする。範囲が広すぎると、年表が原文と無関係なコミットで埋まるためである。
  - 原文がリポジトリの直下にある。
  - ディレクトリが、原文と無関係なファイルの集積（ノートの置き場、文書の置き場など）である。
  - 範囲のコミットが500件を超える。
- 原文の名前の変更（移動）: `git log --follow --name-status -- FILE` で変更前のパスを確認する。年表と変更の抽出は、変更前のパスのコミットを含める（`--follow` を使用する）。
- `<data-dir>` と HTML の出力先: 依頼または利用者の設定に準拠する。
- 公開先: 指定がある場合だけ確定する。

`<data-dir>` に既存のデータがある場合は、依頼で区別する。依頼が更新（「差分を反映して」「最新にして」など）の場合は、新規作成ではなく追従である。「上流の更新へ追従する」の節へ進む。依頼が更新ではない場合は、上書きせずに利用者へ確認する。

版の履歴の有無は、この手順で判定する。Git 管理の場合は `references/collect-history.md` で対象ファイルを変更したコミットを取得する（GitHub の API は手順2、ローカルの clone は末尾の節）。Google Docs の場合は Google Drive の `list_file_revisions` で版の一覧を取得し、版ごとの本文を取得できるかを確認する。ほかの性質は原文の内容に依存するため、手順2の末尾で判定する。

### 2. 原文を取得し、節を抽出する

原文の全体を取得できない場合（権限がない、一部のタブを取得できないなど）は、作業を中止して報告する。取得できた部分だけでデータを作成しない。版の履歴がある場合も、節は最新版だけから抽出する。

**Google Docs**

1. URL の `/document/d/<ID>/` の ID を `documentId` として、Google Docs の MCP の `read_doc` で取得する。
2. 結果は大きいため、全文を文脈に展開せず、ファイルへ保存する。実行環境が結果をファイルへ退避した場合は、そのファイルを使用する。
3. `jq -f <skill-dir>/scripts/extract-gdoc.jq <保存したファイル> > <data-dir>/sections.json` で下書きを作成する。節は見出しごとに分割され、子タブも抽出される。`tab` はタブの経路（「親 / 子」）、`id` は `<タブ ID>/<見出し ID>`、タブの冒頭の本文は `<タブ ID>/top` の「（冒頭）」の節になる。jq がエラーを返却した場合や節が0件の場合は、保存したファイルの最上位の構造（`tabs` を含む文書の JSON が最上位か `content` に格納されているか）を確認し、文書の JSON を抽出してから再実行する。
4. 下書きの `tab` の一覧を原文のタブと照合する。範囲を限定した場合は、範囲外の節を `sections.json` から除外する。

**Markdown**

1. `node <skill-dir>/scripts/extract-md.mjs <file.md> [--url <URL>] [--tab <分類>] [--items] [--arrows] [--ids] > <data-dir>/sections.json` で下書きを作成する。`id` は見出しの経路のスラッグ（例: `playbooks/investigation`）である。
2. GitHub のファイルは、`--url` に `https://github.com/<owner>/<repo>/blob/<sha>/<path>` を指定する。`<sha>` は抽出した版のコミットとし、`meta.source.url` と同じ値にする。
3. ローカルの clone が最新でない場合は、最新版を `https://raw.githubusercontent.com/<owner>/<repo>/<sha>/<path>` から取得してファイルへ保存し、そのファイルから抽出する。
4. 節の粒度を確認する。網羅の検査は節の単位で機能するため、1つの節が多数の規定を含むと、枝にしていない規定を検出できない（完成例の poteto-mode は、見出しが7件の原文を `--items --arrows` で56節に分割した）。次の手順でオプションを決定する。
   1. オプションなしで抽出し、1節に5件以上の規定を含む節があるかを確認する。ない場合は、オプションを付与しない。
   2. ある場合は、その節の規定の書式を確認する。太字の見出し語で開始する項目（`**名前.** 本文`、`**名前**. 本文`）が並ぶ場合は `--items`、「条件 → 動作」の箇条書きが並ぶ場合は `--arrows`、ID で開始する箇条書き（`R5-1: 本文`、`AC3: 本文`）が並ぶ場合は `--ids` を付与する。矢印がパスの対応や変換を表す文書（`` `@/` → `src/` `` など）には `--arrows` を付与しない。
   3. 付与した場合は、分割された節の題を全件確認する。題が文の断片になっている節、または規定ではない記載（技術構成の一覧など）が分割されている節があれば、そのオプションを除外して再抽出する。
   4. 番号付きの箇条書きや、太字のない箇条書きは分割されない。その場合も節を手作業で分割しない。粒度が粗い節が残存する場合は、その節の規定のうち枝にしなかった規定を `note` の指摘に記載し（手順4）、手順9でその節を報告する。

**そのほかの形式（org-mode、Word、HTML など）**

1. pandoc で GitHub 形式の Markdown へ変換し、Markdown の手順で抽出する。例: `pandoc -f org -t gfm --wrap=none <file.org> -o <作業用ディレクトリ>/<名前>.md`（Word は `-f docx`、HTML は `-f html`）。変換後の Markdown は作業用ディレクトリに置き、`<data-dir>` に置かない。
2. 変換で見出しの階層や太字が保たれたかを、変換後の Markdown の見出しの一覧で確認する。org-mode の `:PROPERTIES:` や `#+TITLE:` などのメタデータは本文に残らない。変換の痕跡（org-mode の `#+OPTIONS: \n:t` による行末の `\`、`(id:…)` の形へ変換された内部リンク、未対応のオプションの警告など）は、節の本文に残してよい。節を手作業で修正せず、報告に記載する。
3. `--url` には原文の所在（リポジトリの URL など）を指定する。見出しのアンカーは変換後の Markdown のもので、原文のアンカーと一致しない場合がある。一致しない場合は報告に記載する。
4. pandoc を使用できない場合は、作業を中止して報告する。節を手作業で作成しない。

**全ての原文**

- 抽出に使用したコマンド（変換・取得のコマンドを含む）を、`meta.extract` に記載する。追従（R1）は、この記載のとおりに再抽出する。ローカルのパスは `<原文>` などの仮の名前に置換する。
- 節の `id` を変更しない。`text` は原文のままとし、要約しない。節を手作業で作成しない。
- 規定を含まない節（参考文献、目次、改訂履歴、機能名だけの一覧など）に、除外の理由を `skip` として記載する。本文が空の節は見出しだけの節として網羅の検査の対象外になるため、`skip` は不要である。
- ほかの節の規定を要約・再掲する節（成功条件、受け入れ基準、対象外の一覧など）は `skip` にしない。再掲された規定の枝の `src` に含め、再掲にない内容（受け入れ基準の期待結果など）だけを新しい枝にする。枝にしなかった再掲は `note` に記載する。
- 全ての節を通読し、「文書の性質と使用する機能」の表で、版の履歴以外の性質を判定する。判定ごとに、根拠とした節を記録する。

### 3. 状態を設計する

1. 適用の対象が複数ある場合は、対象を `meta.variants` に記載する。各枝の `for` は手順5で記載する。
2. 状態は、作業・処理の局面か契機で集約する。局面（受付、審査、発行、設計、実装、検証など）は、処理の順に `flow` へ左から記載する。処理の流れと独立して発生する契機（管理操作、質問したくなった、作業を委任するなど）は `any` に記載し、領域の名前を `meta.anyLabel` に記載する。
3. `flow` の順序は、原文の処理の順序と、「実装前」「コミット前」のような前後関係の記載から構成する。
4. `meta.json` に、`title`、`slug`、`brand`、`name`、`source`（原文の題名と URL）、`transitions`、`kinds` を記載する。`legend` と `levelLabels` は任意である。
   - `slug` は、ブラウザに確認済みの記録と用途の選択を保存するキーである。ほかのページと重複しない値にする。
   - 遷移先の種別は、呼び出すスキルやツールは `skill`、原則や規範は `prin`、別の手順書は `pb`、それ以外の動作は `act`、禁止・停止・拒否は `stop`、モデル名や値などの識別子は `m` とする。原文に固有の結果（発行する書類、コマンド、参照する文書など）は、`kinds` に組み込みの外観を指定して定義する（例: コマンドは外観 `skill`、参照する文書は外観 `pb`）。凡例の名前は `kinds` の表示名で決まり、`legend` を記載した場合はそちらを優先する。
   - `level` の表示名を原文の語（「原則」「推奨」など）にする場合は、`levelLabels` に記載する（手順5）。
5. `transitions` が `"explicit"` の場合は、局面の間の遷移を、遷移先が `["state", 状態名]` の枝として記載する。用途ごとに、`flow` の先頭の状態から正常系の道筋を遷移で追跡できるようにする。用途によって入口が異なる場合は、先頭に用途を選択する状態を配置する。原文が明記していない遷移を補完した場合は、`inferred` に理由を記載する（例: 「原文は申請の審査の後に許可証を発行する遷移を記載していない」）。

状態の名前と `flow` の順序は、原文にない語と構成を含む。原文が処理の順序を定義している場合も、局面の区切りは作成者の判断を含む。`issues.json` に `note` の指摘を1件記載し、原文の構成、作成者が命名した状態の名前と順序、1つの節の規定を複数の状態へ分割した箇所を記載する（完成例 poteto-mode の i10）。

### 4. 枝を記載する

対象は原文の本文だけで、参照先のファイルや文書の内容は展開しない。展開すると図が原文の範囲を超え、読み手が記載の箇所を確認できなくなる。

- 「X の場合は Y」「Y の前に Z」という規定を、1件ずつ枝にする。`g` は条件を体言止めの短い句で、`to` は遷移先を記載する。
- 1つの規定に複数の条件がある場合は、条件ごとに枝を分割する。
- 条件を持たない規定（チェックリストの項目、全ての場合に適用する規則など）は、`g` を「常に」とする。原文の副詞（「必ず」など）を条件の代わりに使用しない。
- 条件の対象を節の題から補完した場合（節「添付ファイル」の「上限を超えた場合は…」を「添付ファイルが上限を超過」とするなど）は、`inferred` を記載しない。節の題は原文の記載である。原文にない語で条件を作成した場合だけ `inferred` を記載する。
- 見出しを持たない段落（文書の末尾の注意書きなど）は、抽出の結果の節を `src` とする。段落の内容が文書全体に適用される場合は、適切な状態へ配置し、配置の変更を `note` に記載する。
- 結果が順に発生する場合は、`to` に発生順に記載する（例: `[["act","添付を破棄"],["stop","受け付けない"]]`）。
- 遷移先の表示名は原文の語に準拠する。原文の語が異なる結果（「受け付けない」「許可しない」「禁止」など）は、異なる表示名のまま記載する。ページは `to` が同一のエラーを1つの遷移先へ集約するため、同じ語の語尾の違い（「エラー」と「エラーとする」）だけは表記を統一する。
- 識別子（パラメータ名、方式名、スキル名、ファイル名、モデル名など）は原文の表記のまま使用する。原文にない表記（省略形、別名、表記の統一）を作成しない。節によって表記が異なる場合は各節の表記のまま記載し、`conflict` の指摘を記載する。
- `src`: 全ての枝・エラー・記載済みの欄に、根拠の節の ID を記載する。補完した遷移には、補完の根拠とした節を記載する。
- `inferred`: 原文が明記していない結果・条件・遷移を補完した場合は、必ず理由を記載する。原文が結果を明記していない箇所に「エラー」などの結果を補完した場合も該当する。発生しやすい誤りは、「必須とする」とだけ記載された項目に「エラー」を補完し、`inferred` を付与しないことである。
- `gap`: 1つの状態に枝が多い場合は、意味のまとまりの先頭の枝に `true` を記載する。

次の場合は、`note` の指摘に記載する。

- 規定を、原文の節が属する局面と異なる状態へ配置した。
- 節を `src` に含めたが、その節の規定の一部を枝にしなかった。複数の規定を1つの枝に集約した場合を含む（完成例 poteto-mode の i11・i13）。網羅の検査は節の単位のため、指摘に記載しないと読み手が欠落を検出できない。

### 5. 性質に応じた機能を記載する

手順1・2で該当すると判定した機能だけを記載する。

**要求の拒否（****`errors`****）**

- 区分は、要求を拒否するかで決定する。要求の拒否（エラーとする・受け付けない・許可しない・登録できない）は `errors` に配置する。拒否ではない否定（「取り消せない」「発行しない」「提供しない」）は `rules` に配置する。区分は遷移先の種別と独立しており、`rules` の遷移先に `stop` を使用してよい。
- エージェント向けの指示書の「必ず停止する」「確認を待つ」は、要求の拒否ではない。`rules` に `stop` で配置する。これらは最重要の規則であることが多く、`errors` に配置すると既定で折り畳まれて表示されない。
- `errors` の全件について、`src` の節が結果を明記しているかを確認し、明記していない場合は `inferred` を記載する。
- 拒否が判定表の欄に該当する場合（条件の組み合わせで拒否が決まる場合）は、判定表の欄に配置し、`errors` に重複して記載しない。

**判定表（****`table`****）**

条件が2つ以上の軸の組み合わせで決定される規定（会員か否か × 契機など）がある状態だけ、`table` を作成する。

- 軸が3つ以上の場合は、行または列の値に組み合わせを記載する（例: 「会員・有効期限の設定あり」）。
- 原文に記載のない組み合わせは、`to` も `na` も記載しない未規定の欄とし、`issue` で `gap` の指摘と関連付ける。
- `na` は、組み合わせとして該当しない欄だけに使用する。記載がないことを `na` で表現しない。
- 欄の結果の一部だけが記載されている場合は、列（または行）を結果の項目ごとに分割する（例: 「使用時の有効期限」と「使用時の新しい整理券」）。
- 記載済みの欄の全件について、`src` の節が結果を明記しているかを確認し、明記していない場合は `inferred` を記載する。

**用途（****`for`****）**

`for` は、規定が適用される用途である。原文が用途ごとにタブ・節を分割している場合は、規定が記載されたタブ・節の用途とする。

- ある用途の規定を、ほかの用途へ展開しない。ある用途のタブの規定がほかの用途にも妥当と判断できる場合も、`for` は記載された用途だけにする。
- 規定が適用の対象の用途を明記している場合（ある用途のタブが「ほかの用途では提供しない」と記載している場合など）は、明記された用途を `for` に記載し、配置を `note` の指摘に記載する。
- 適用範囲が曖昧な記載（あるタブの規定が、ほかの用途にも適用されるかを記載していない場合など）は、記載のある用途に限定する。そのうえで `note` または `ambiguous` の指摘を記載し、手順9で利用者に判断を依頼する。
- 全用途に共通のタブ・節の規定は、その記載が対象とする用途を `for` に記載する。
- `meta.variants` を定義した場合は、版の履歴で削除済みの枝を含む全ての枝・エラー・記載済みの欄に `for` が必要である。原文が対象を分割していない場合は、`meta.variants` と全ての `for` を記載しない。

**規格・原則（遷移先か `why` か）**

- 原文が規格・原則を、実施する動作として指示している場合（例: 「principle-X を適用する」「この手順書に準拠する」）は、遷移先にする（原則は `prin`、手順書は `pb`、スキル・ツールは `skill`）。
- 原文が規格・方針を、別の結果（エラー、値）の根拠として引用している場合（例: 「ISO 8601 に準拠し、エラーとする」）は、`why` に記載する。`to` に配置すると「→ ISO 8601 → エラー」と表示され、処理の段階と誤読される。

**要求の強さ（****`level`****）**

| 原文の語の例 | `level` |
| --- | --- |
| 必須、必ず、しなければならない、禁止 | 記載しない（既定の `must`） |
| 望ましい、推奨、原則として、通常は | `should` |
| してもよい、任意、必須としない、緊急時に限り可 | `may` |
| 当面実装しない、現状では行わない | `deferred` |
| 試験的に、ドラフト | `trial` |

表示名を原文の語にする場合は `meta.levelLabels` に記載する（例: `{"should": "原則・推奨"}`）。表にない語は、最も近い行を選択し、`note` の指摘に対応を記載する。

**標準との関係（****`std`****）**

`eq`（標準どおり）、`strict`（標準より厳格）、`dev`（標準からの逸脱）と、標準の規定を記載する。標準の規定は、原文または標準の本文に基づいて記載する。

### 6. 版の履歴を記載する（版の履歴を取得できる場合）

1. **年表**: `references/collect-history.md` のコマンドで、範囲内の全コミットと、対象ファイルを変更したコミットを取得し、`timeline.json` を作成する。ローカルの clone を使用する場合の行数・名前付きの単位の取得方法と、件名の接頭辞の扱いも同じ資料に記載している。Git 以外の版の履歴は、版の一覧と版ごとの本文の差分から、同じ形式で作成する。件名は読み手の言語へ翻訳する。翻訳では、スキル名・ファイル名・モデル名などの識別子を原文のまま保持し、原文にない補足を追加しない。
2. **meta**: `repoUrl`（GitHub 以外は `link`）、`file`、`fileLabel`、`areas` を記載する。`areas`（変更の区分）は、原文の節の構成から決定する。名前付きの単位の件数の推移を表示する場合は `series` を記載する。
3. **変更の抽出**: 対象ファイルを変更した各コミットについて、差分から「何が追加・変更・削除されたか」を抽出し、`hist.json` を作成する。意味の変化がない文言の修正は、コミットごとに1件へ集約する。原文の移動・名前の変更だけのコミットは、文言の整理に使用する区分に「原文の移動」の変更（`c`）を1件記載する（build は変更が空の版をエラーにする）。
   - 対象ファイルを変更したコミット（年表の全件ではない）が20件を超える場合、または対象ファイルの差分の合計が約1,000行を超える場合は、古い順に12件前後の束へ分割し、束ごとにサブエージェントへ委任する。差分の読み取りは件数に比例して文脈を消費し、主セッションで実施すると後半の精度が低下する。これより小さい場合は、主セッションで全差分を読み取る（委任しても、対応付けのために主セッションで差分を読み直すことになるため）。差分の合計は `git -C <repo> log --numstat --format= -- FILE` の行数の合計で見積もる。依頼文と結合の方法は `references/extraction-brief.md` に準拠する。意味の読み取りが成果物の中核のため、判断に強いモデルを指定する。
   - 委任は `areas` の決定の後に開始でき、手順3〜5と並行して実施してよい。
4. **対応付け**: 各枝・エラー・記載済みの欄の `h` に、その規定を追加・変更・削除したコミットと、`hist.json` の何番目の変更に対応するかを記載する。この対応が、時点の再生と、カードから枝への移動を成立させる。
   - 最初の対応は追加（`a`）で、その規定を導入したコミットを指定する。意味が変化したコミットは変更（`c`）として追加する。
   - `h` の種別は枝から見た変化で、`hist.json` の変更の種別と一致しなくてよい。例: 既存の規定の変更（`hist` の `c`）で新しい条件が生じ、新しい枝を作成した場合、その枝の `a` はその変更を参照する。規定の書き換え（`hist` の `c`）で旧来の枝が意味を失った場合、その枝の `d` はその変更を参照する。
   - 削除された規定は、現行の規定と同じ粒度（1規定1枝）で枝にする。削除されたコマンドの一覧であれば、コマンドごとに枝を作成する。
   - **後に削除された規定も枝として記載する**。`hist.json` の削除（`d`）と、動作を置換した変更を確認し、最新版の原文に存在しない規定を枝として追加して、削除したコミットを `d` で指定する。枝は存在した期間だけ表示される。これを省略すると、過去の時点の図から当時の規定が欠落する。
   - 削除済みの枝は `src` を必要としない。記載する場合は、最新版に同じ見出しが存続している節だけを指定する。
   - 導入したコミットを特定できない枝は、`h` を空にする。全ての時点で表示される枝になる。推測で `h` を記載しない。`h` が空の枝と理由を `note` の指摘に記載する。
5. **注目**: `timeline.json` の `star` を、次のいずれかに該当するコミットへ付与する。規定の変化を伴わないコミット（バージョンの更新だけ、表記・体裁・文言の整理、原文以外の文書だけの更新、既定値の版の更新）は対象外とする。原文自体が文書の場合も、規定が変化するかで判定する。この分類は上流の区分ではなく作成者の判断であり、手順9で基準を報告する。
   - 名前付きの単位（スキル、手順書、章など）を追加または削除した。
   - 規定の対象の振る舞いが変化する。起動条件や規則の追加と削除、既定値の系列の変更、構造の変更が該当する。

### 7. 指摘を記載する

`issues.json` に、原文の記載を根拠とする指摘を記載する。推測で事実を作成しない。`body` には、どの節が何を記載し、何を記載していないかを、節の題を「」で引用して記載する。

- `conflict`: 原文の食い違い。節によって識別子・値・規定が異なる。
- `gap`: 記載のない点。判定表の未規定の欄、到達できない状態、違反時の結果、ある用途の規定の欠落など。
- `ambiguous`: 解釈が分かれる記載。適用範囲、「[検討中]」の付記など。
- `note`: 作成者の注記。状態の名前と構成（手順3）、配置の変更と枝にしなかった規定（手順4）、記載のある用途への限定（手順5）、`h` が空の枝（手順6）。

各指摘の `src` に関係する節を記載し、関係する枝・欄の `issue` から参照する。`issues.json` の `src` は網羅の検査の対象にならないため、節の網羅は枝・エラー・欄の `src` で確保する。

### 8. 生成して検査する

```bash
node <skill-dir>/scripts/build.mjs <data-dir> <out.html>
```

build は、データの形式、参照の整合、節の網羅、版の履歴の対応付けの規則を検査する。問題が1件でもある場合は HTML を出力しない。出力は次のとおり対応する。

| 出力 | 対応 |
| --- | --- |
| `error:` | 修正して再実行する。参照されない節が規定を含む場合は、枝として記載する。`skip` は規定を含まない節だけに使用し、検査の通過を目的に使用しない |
| `note: 未規定 (issue なし)` | 未規定の欄に `gap` の指摘を関連付ける |
| `note: src を持たない枝` | `src` を記載する |
| `note: hist …: 変更の was / now の片方が空` | 該当の変更を確認する。差分の内容のとおりであれば修正しない |
| `枝に対応しないコミット:` | 意味の変化がない更新だけであれば正常である。規定の追加や削除を含むコミットがある場合は、手順6の対応付けが不足している |
| 件数の行（`commits:`・`changes:`・`states:`・`errors:`・`inferred:`・`sections:`・`issues:`） | 手順9の報告に使用する |

`transitions` が `"explicit"` の場合は、build が到達性を出力する。用途ごとに、`flow` の先頭の状態から、`for` にその用途を含む `["state", …]` の遷移を追跡し、その用途の枝を含む `flow` の状態のうち到達できた件数を `到達 (<用途>): 到達 / 対象` で出力する（版の履歴がある場合は、最新版で存在する枝だけが対象）。到達できない状態は `note: 到達できない状態` に出力される。該当する状態には、原文の記載を根拠に遷移を補完して `inferred` を記載するか、`gap` の指摘を記載する。

描画を確認する。

- ブラウザ（エージェントが操作できるブラウザ、headless の Chrome など）を使用できる場合は、HTML を表示し、描画と例外を確認する。
- サンドボックスなどでブラウザを使用できない場合は、jsdom を導入し、読み込み時の例外を確認する。終了コードが 0 で、出力の `errors` が空であれば通過とする。出力の `rules` はエラーと判定表の欄を含む要素の件数で、build の `rules:` と一致しない。jsdom はレイアウトを計算しないため、この確認は描画の確認にならない。

```bash
npm install --prefix <作業用ディレクトリ> --cache <書き込み可能な一時ディレクトリ> jsdom@24.1.3
NODE_PATH=<作業用ディレクトリ>/node_modules node <skill-dir>/scripts/domcheck.cjs <out.html>
```

エンジン（`assets/template.html` と `scripts/`）は、利用者の確認を経た動作のため、依頼がない限り変更しない。変更した場合は、`NODE_PATH=<作業用ディレクトリ>/node_modules node <skill-dir>/tests/run.mjs` を実行し、全件の成功（末尾の「すべて成功」）を確認する。このスクリプトは、`examples/fixture`、`tests/history`、`tests/legacy`、`tests/invalid`、`examples/` の完成例を検査する。

### 9. 公開して報告する

公開先の指定がある場合だけ、出力した HTML を公開する。公開の範囲の指定がない場合は、本人のみとする。出力先・公開先に同じ `slug` の既存のページがある場合は、追従で同じページを更新する場合を除き、上書きせずに利用者へ確認する。

報告には次を含める。

- 件数: build の出力（状態、枝、エラー、判定表の欄と未規定の欄、`inferred`、節の網羅、指摘。版の履歴がある場合はコミット、対象ファイルを変更したコミット、注目、変更と枝に対応した変更）。
- 作成者が命名した名前と構成: 状態の名前、`flow` の順序、原文の節と異なる状態へ配置した規定、注目の基準（版の履歴がある場合）。
- 使用した機能と、性質の判定の根拠: 表の各行の判定と、根拠とした節または取得の結果（例: `list_file_revisions` が空の結果を返却した）。
- `inferred` の主な箇所: 補完の種類（違反時の結果、局面の間の遷移など）ごとの代表例と件数。
- 指摘の一覧: 種類ごとの題。
- 確認していない事項: ブラウザでの描画を確認していない場合はその旨。抽出を委任し、対応付けを差分と照合していない場合はその旨。`h` が空の枝。年表の追加・削除の行数が範囲外のファイルを含む場合はその旨。粒度が粗く、網羅の検査が規定の単位で機能しない節。
- 図の制約（版の履歴がある場合）: 枝の文面は最新版のもので、過去の時点でも当時の文面には復元されない。
- 利用者に判断を依頼する点: 記載のある用途に限定した規定、`ambiguous` の指摘、状態の名前と構成、`h` が空の枝の規定の削除（追従の場合。G4）。

## 上流の更新へ追従する

版の履歴がない原文は「原文の節を再抽出する」の手順だけで追従する。Git 管理の原文は「Git の新しいコミットへ追従する」の手順で追従し、その中で節の再抽出を実施する。完了条件は新規作成と同じである。この節の「R1」〜「R8」と「G1」〜「G5」は、次の2つの一覧の各項目を指す。「手順N」は「## 手順」の各手順を指す。

### 原文の節を再抽出する

- R1. 旧 `sections.json` を退避する。最新の原文を手順2のとおり取得し、`meta.extract` に記載したコマンド（変換、`--url`・`--tab`・`--items`・`--arrows`・`--ids`、範囲の限定）で再抽出する。`meta.extract` がない場合は、旧 `sections.json` の節の分割と `url` からオプションを推定し、同じ節の集合を再現できることを確認してから進める。旧 `sections.json` の `skip` は、同じ `id` の節へ引き継ぐ（抽出は `skip` を出力しないため）。
- R2. 旧と新の `id` の集合を比較し、旧だけにある節と新だけにある節を本文で照合して、節を「追加」「削除」「見出しの変更」「本文の変更」に分類する。ID の安定性は原文によって異なる。
  - Google Docs: 見出し ID は見出しの文言を変更しても変化しない。見出しの変更は `title` の差分として検出される。見出しが規定を含む場合（「Proof Key for Code Exchange を必須とする」など）があるため、見出しの変更は本文の変更と同じく R4 の対象にする。
  - Markdown: ID は見出しの経路のスラッグである。見出しの文言を変更すると、その節と下位の全ての節の ID が変化する。`--ids` の項目は ID が変化しない限り安定する。`--items`・`--arrows` の項目は、題の先頭の8語（語の区切りがない日本語などの題は先頭の24文字）が変化すると ID が変化する。同じ経路の節に付与する `2`・`3` は出現順のため、節の挿入や削除で変化する。
- R3. 見出しの変更で ID が変化した節は、`machine.json` と `issues.json` の `src` の旧 ID を新 ID へ置換する。
- R4. 本文が変化した節を `src` に含む枝・エラー・欄を再確認し、`g`・`to`・`inferred`・判定表の欄を最新版の文面へ更新する。新しい規定は、手順4・5に準拠して枝として追加する。
- R5. 削除された節を参照する枝は、規定が存続しているかを確認する。規定が別の節へ移動した場合は、`src` をその節へ置換する。規定が削除された場合は、版の履歴がなければ枝を削除する。版の履歴があれば枝を削除せず、G4 で `d` を追加する。
- R6. 追加された節の規定を、手順4・5に準拠して枝にする。
- R7. `src` に変化した節を含む指摘を再確認する。解消した指摘は削除し、その指摘を参照する `issue` も削除する。
- R8. 手順8・9を実施する。報告では、節の差分の件数（追加・削除・見出しの変更・本文の変更）と、状態機械に反映した変更を記載する。

### Git の新しいコミットへ追従する

- G1. `timeline.json` の先頭のコミットより新しいコミットを収集し、先頭へ追加する。注目を手順6の基準で判定する。
- G2. 対象ファイルを変更した新しいコミットだけを対象に、変更を抽出して `hist.json` へ追加する。既存の変更の配列の順序は変更しない。
- G3. `meta.source.url` と `extract-md.mjs` の `--url` の sha を最新のコミットへ更新し、R1〜R7 を実施する。枝の追加、`g`・`to` の更新、削除された規定の確認は、この中で実施する。
- G4. G3 で追加・更新した枝と、規定が削除された枝の `h` に、G2 で追加した変更への対応を記載する。新しい規定には `a`、意味が変化した枝には `c`、削除された規定には `d` を追加する。削除された規定の枝は削除しない。枝を削除すると、過去の時点の図からその規定が欠落する。削除した枝の `src` は、最新版に同じ見出しが存続している節だけにする。`h` が空の枝の規定が削除された場合は、`a` がないため `d` を記載できない（build のエラーになる）。導入したコミットを推測で記載せず、手順9で利用者に判断を依頼する。
- G5. 手順8・9を実施する。報告では、追加したコミットと、状態機械に反映した変更を記載する。

## ページの動作

テンプレートの動作は次のとおりである。データの各項目の表示箇所を把握するために記載する。

- **キャンバス**: ドラッグとスクロールで移動し、ピンチ（Ctrl・⌘ とホイール）で拡大・縮小する。`+` `−` `0` で拡大・縮小・全体表示、矢印キーで移動、`?` でキー操作の一覧を表示する。左上に `meta.brand`（ない場合は原文の題名）を表示し、`meta.source.url` へリンクする。状態機械の枠に `meta.name` を表示する。
- **状態**: `flow` を左から右へ、`any` を `meta.anyLabel` の下段へ配置する。`transitions` が `"flow"` の場合は `flow` の状態を配列の順に接続する。`"explicit"` の場合は、遷移先が `["state", …]` の枝から、その状態へ矢印を描画する。遷移先の状態名を選択すると、その状態へ移動する。
- **遷移先**: `meta.kinds` の外観で色と形を区別する。補足は、外観が `pb` の場合は表示名の右に表示し、それ以外の外観ではホバーで表示する。
- **エラー**: 状態の下部に、「エラー・不可」の見出しと件数を表示する折り畳みとして配置する。`to` が同一の枝は、条件を列挙して1つの遷移先へ集約する。見出しの選択で開閉する。選択中の枝か、時点で強調中の枝を含む場合は自動で展開する。
- **判定表**: 記載済みの欄は遷移先を、`na` の欄は「—」（ホバーで理由）を、未規定の欄は「未規定」を警告の色で表示する。
- **枝の印**: `why` は短い名前（ホバーで詳細）、`std` は `=`・`>`・`≠`（ホバーで標準の規定）、`level` が `trial` の場合は `β` を表示する。`should`・`may`・`deferred` は枝の様式で区別し、ホバーで表示名を表示する。`inferred` を記載した条件は「補完」の様式で表示し、ホバーで理由を表示する。`issue` は指摘の種類の印を表示し、選択すると指摘へ移動する。凡例には、使用している印だけを表示する。
- **用途**: 上部の「すべて」と各用途の選択肢で、表示を用途ごとに限定する。「すべて」では、全ての用途に適用されない枝に、適用する用途の印を表示する。用途を選択すると、その用途を `for` に含まない枝・欄と、表示する枝がない状態を非表示にする。選択した用途は `slug` ごとにブラウザに記憶する。`v` キーでも用途を順に選択できる。
- **時点**（`timeline.json` がある場合だけ）: 下部のスライダーと再生ボタンで、初版から最新版まで時点を移動する（`h` `l` で1件ずつ、`g` `G` で初版・最新版、Space で再生・停止）。その時点で存在しない枝と、表示する枝がない状態は非表示になる。削除した版の時点では、枝を取り消し線付きで表示する。選択中の版に対応する枝・エラー・欄を、種別に応じた色と記号（+ \~ −）で強調する。枝の文面は常に最新版で、選択中の時点より後に意味が変化する枝には ⟳ を表示する。
- **更新タブ**（同上）: 選択中の版の変更をカードで表示する。カードは折り畳んだ状態で、選択すると変更前後の文面を展開し、対応する全ての枝が収まる位置へ移動する。カード内の状態名のボタン（`n` `N`）で個別の箇所へ移動する。選択中のカードを再度選択すると解除する。「差分」「最新」の切り替え（`d`）の「最新」は、記号と、その時点で削除した枝を非表示にする。カードに確認済みの印（`c`）を付与でき、「未確認」（`u`）で未確認のカードだけを表示する。確認済みの記録は `slug` ごとにブラウザに保存する。
- **全履歴タブ**（同上）: 全ての版を月ごとに表示し、週ごとのコミット数の推移の図に `meta.series` の件数の推移を併記する。「★ 注目」「対象ファイル（`meta.fileLabel`）」「すべて」の絞り込み、検索（`s`）、並び順の切り替えがある。対象ファイルを変更した版を選択すると、更新タブとキャンバスがその時点へ移動する。
- **原文タブ**（`sections.json` が空でない場合だけ）: 節を `tab` ごとに表示し、各節を参照する枝の件数を表示する。節を選択すると本文を展開し、その節を `src` に含む枝を選択して移動する。節の題は原文の該当箇所へリンクする。キャンバスの枝を選択すると、その枝の `src` の節を表示する。
- **指摘タブ**（`issues.json` が空でない場合だけ）: 指摘を種類ごとに表示する。指摘を選択すると本文と関係する節を表示し、その指摘を `issue` に含む枝と欄へ移動する。
