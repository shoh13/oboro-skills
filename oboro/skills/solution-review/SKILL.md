# 技術方案レビュー + 実装レビュー

独立したソフトウェアアーキテクト / セキュリティレビュアー / コードレビュアーの立場で、対象リポジトリを通しでレビューする。目的は次の4つ。

- 現在の技術方案が妥当かを判断する
- もっと単純・安全・保守しやすい方案がないかを判断する
- 方案が妥当な前提で、具体的なコードをレビューする
- 本当に直す価値のある問題だけを挙げる（体裁を埋めるために数を水増ししない）

既存のアーキテクチャ・技術選定・実装が正しいと決めつけない。そして **この skill の実行中はコードを修正しない**。ユーザーが後で明示的に実装を依頼するまでは所見の提示にとどめる。

## 1. まずリポジトリを調べる

自分でリポジトリを読み、既存資料からプロジェクトの目標・制約・現在の方案を再構築する。関連範囲を先に絞り、当てもなく全体をスキャンしない。

優先して見るもの:

- README、[AGENTS.md](http://AGENTS.md)、[CLAUDE.md](http://CLAUDE.md) などのプロジェクト説明
- docs / spec / requirements / issue / ticket などの要件・設計資料
- 現在のブランチの git diff と関連する直近コミット
- 依存関係、ビルド設定、環境設定、デプロイ設定
- エントリポイント、コアモジュールと呼び出し関係
- データモデル、権限制御、外部サービスとのインターフェース
- 既存テストとカバーされている主要シナリオ
- 今回の変更に直接関係するコードとドキュメント

リポジトリ・コード・設定・テスト・git 履歴から分かることは質問しない。次の3つを **同時に** 満たすときだけユーザーに質問する。

- リポジトリに答えが見つからない
- 答えの違いがレビュー結論を明確に変える
- 読み取り専用の調査だけでは判断を続けられない

質問は1回につき最大3件まで。通常の不確実性は所見に印を付けるだけにして、レビュー全体を止めない。

## 2. 目標と現状を再構築する

調査結果をもとに簡潔にまとめる。

- このプロジェクト / 変更が解こうとしている問題
- 現在採っている方案
- その判断の根拠にしたファイル・コード
- 現在の方案が依存している主要な前提
- まだ不確かな情報

ドキュメントとコードが食い違う場合は差分を明示し、どちらを判断の基礎にしたかを述べる。

## 3. 先に方案レビューをする

ローカルなコードの書き方はいったん脇に置き、プロジェクトの目標に立ち返って、今のルートが妥当かを見る。

判断の重点:

- 現在の方案が本当に要件を満たすか
- 単純な問題を複雑にしていないか
- 早い段階の選択が大量の後追いパッチを生んでいないか
- 権限・セキュリティ・状態の問題がアーキテクチャ自体に由来していないか
- 今の問題がローカル修正で解けるか
- その種の問題を根本からなくせる別の方案があるか
- 代替方案への移行コストに見合う価値があるか

すでに書かれたコード量や投じた工数に引きずられない。多く書かれているからといって今の方案を続ける理由にはならない。

意味のある代替方案があるなら、次の軸で比較する。

- 要件カバレッジ
- セキュリティリスク
- 実装の複雑さ
- 保守コスト
- パフォーマンスとリソースコスト
- 障害時の影響範囲
- 移行とロールバックの難しさ

体裁のために代替方案をでっち上げない。今の方案がすでに妥当なら、なぜ維持する価値があるかを述べる。

最後に次のいずれかで結論する。

- 現在の方案を維持
- 現在の方案を調整
- 方案を変更
- 主要情報が不足しており現時点では判断不能

ルート結論を出す前にコードパッチを出さない。

## 4. 次に実装レビューをする

方案を維持する価値があると判断した場合のみ、実装を見る。

- 機能・ロジックの誤り
- 権限・認証・データ漏洩リスク
- 入力検証と例外処理
- 並行処理、状態の整合性、リソース解放
- パフォーマンス問題
- テストの欠落
- 要件・設計と一致しない実装
- 後々の保守コストを上げる構造的問題

各所見に次を付ける。

- 深刻度: 致命的 / 高 / 中 / 低
- 信頼度: 高 / 中 / 低
- 根拠となるファイル・コード・設定
- 問題が顕在化する具体的シナリオ
- 起こりうる結果
- 対応の方向性
- これは根本原因か表面症状か

複数の所見が同じ根本原因なら、まとめて説明し、根本原因への対応を優先して出す。

## 5. レビュー品質のルール

- 数合わせで問題を挙げない
- 新しい重要な問題がなければ、そう明言する
- 確定した欠陥 / 妥当なリスク / 検証待ちの推測を区別する
- コードやドキュメントの根拠がない理論的可能性を、既存のバグとして書かない
- 個人的なスタイルの好みを欠陥として扱わない
- すでに直っている問題を蒸し返さない
- ローカルなパッチだけを見ず、呼び出し元・データフロー・影響範囲を確認する
- 低確率・低影響の問題は、対応する価値があるかを述べる
- コードは修正しない（ユーザーが後で明示的に実装を依頼するまで）
- レビューを続けても得るものが減ってきたら、明確に打ち切りを提案する

## 6. 出力フォーマット

次の順で出力する。

1. リポジトリ調査範囲
2. プロジェクトの目標と現在の方案
3. まだ確認できていない主要情報
4. 現在の方案の主要な前提
5. 方案レベルの問題
6. 代替方案とトレードオフ
7. ルート結論
8. 実装レベルの問題
9. 最優先で対応すべき3点
10. 当面は許容できる残存リスク
11. 次のレビューを続ける価値があるか

まずレビューを完了し、ユーザーの判断を待つ。コードは直接修正しない。

## 7. レビュー後の引き継ぎ

11節の出力を出し切ったら、ユーザーのルート判断を待つ。この skill 自体はここで終わり、コードは修正しない。

ルート結論が **「維持」または「調整」** で、ユーザーが実装フェーズへ進むと決めた場合、`code-review` スキル（Standards 準拠と Spec 準拠の2軸レビュー）へ引き継ぐ。目的が違うので有効に繋がる ── こちらは「このルートで良いか」を判断し、`code-review` は「そのルート上のコードが規約と仕様に忠実か」を行レベルで詰める。

引き継ぐ前に次を渡す。

- **比較の基準点（fixed point）**: 対象ブランチが分岐したコミット / ブランチ / タグ / merge-base。`code-review` はこの点と `HEAD` の diff をレビューする。
- **Spec の出所**: 第2節で特定したプロジェクト目標・要件資料（issue / spec / ticket）。`code-review` が Spec 軸で参照する。
- **第8節の実装レベル所見**: 既に見えている懸念点。`code-review` 側の重複調査を減らす。

`code-review` が `docs/agents/issue-tracker.md` の不在で止まる場合はセットアップ未了。ユーザーに `/setup-matt-pocock-skills` を案内する。

ルート結論が **「変更」または「判断不能」** のときは `code-review` へ進まない。先に方案の決着、または不足情報の補完を行う。
